# GitHub 根目录 README 设计

## 1. 目标

在仓库根目录新增 `README.md`，同时服务两类读者：

- 产品、商务或协作方可以快速理解平台定位、核心能力和当前交付边界。
- 开发、测试和运维人员可以完成仓库克隆、环境准备、本地验证、分支协作，并找到更深入的设计与部署文档。

README 是项目入口，不替代详细设计规范、实施计划和生产 Runbook。

## 2. 内容结构

README 按以下顺序组织：

1. 项目名称、当前阶段和一句话定位。
2. 产品能力概览，分别说明用户工作台与运营控制台。
3. 已实现范围与尚待外部接入的边界。
4. 高层架构和请求链路，以文字及 Mermaid 图表达。
5. Monorepo 目录与各应用、服务、公共包的职责。
6. 技术栈及运行时版本要求。
7. 本地开发：克隆、安装、环境文件、基础设施启动、开发启动和验证命令。
8. Git 协作：默认分支、功能分支、提交和合并要求。
9. 阿里云部署与运维文档入口。
10. 设计规范、实施计划和 Runbook 索引。
11. 安全说明与许可证状态。

## 3. 内容真实性边界

- 只描述 `develop` 分支中可由代码、配置或既有文档验证的能力。
- 火山引擎等真实 AI 视频供应商尚未完成凭据和生产接口接入时，明确标记为“待接入”，不得表述为已上线。
- 微信支付、短信、阿里云资源等依赖商户号、账号、域名、证书或密钥的能力，区分“代码能力已具备”和“外部账号尚待配置”。
- 不宣称生产验收、SLA 达成、合规认证或商业上线已经完成。
- 不写入真实密钥、令牌、商户信息、账号、内部域名或其他敏感信息。
- 不使用无法长期维护的虚假下载量、覆盖率或构建状态徽章。

## 4. 技术说明原则

- 以仓库根目录的 `package.json`、`pnpm-workspace.yaml`、`infra/local` 和现有 Runbook 为命令来源。
- 明确 Node.js 24、pnpm 11.24.0 等版本要求。
- 首选仓库已经提供的 `pnpm verify` 作为统一质量门禁；不会把未经本次核验的命令写成必然成功。
- 本地基础设施和应用启动步骤应区分，避免把生产部署步骤混入快速开始流程。
- 目录表只覆盖长期稳定的一级模块；细节通过链接导向设计规范和 Runbook。

## 5. 协作与分支

- GitHub 默认分支为 `develop`，技术协作从该分支创建 `codex/*` 或团队约定的功能分支。
- `main` 当前保留早期基线，不作为最新开发入口。
- README 的初次提交直接进入 `develop`，后续功能修改建议通过分支和 Pull Request 合并。

## 6. 验收标准

- GitHub 仓库首页能直接展示完整 README。
- README 内所有相对路径链接均指向仓库中存在的文件或目录。
- 安装、验证和主要启动命令与当前仓库脚本一致。
- 产品范围、完成状态和外部依赖没有相互矛盾。
- 文档不包含 `TODO`、`TBD`、占位链接或真实凭据。
- Markdown 格式检查通过，且 Mermaid 图语法可被 GitHub 渲染。

## 7. 非目标

- 本次不修改产品代码、基础设施、CI/CD 或服务配置。
- 本次不创建营销网站、截图、演示视频或英文版 README。
- 本次不接入任何真实 AI 视频供应商、支付渠道或云资源。
